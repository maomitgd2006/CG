# CalibGuard 模型性能对比分析报告（v2.5 全量评测）

- **报告日期**：2026-10-05
- **数据版本**：v2.5（语料扩容 + 归一化层去重后重建划分）
- **评测环境**：云端单节点 RTX 5090（32.6GB）/ fp32 / seed 42；统一超参 lr=2e-5、epochs=3（HPO 网格选优，全部模型共用）
- **评测口径**：test 段 25,049 条全量，恶意 12,596 / 良性 12,453（恶意占比 50.3%）
- **收录方案**：codebert_ft（部署版）、codebert_ft_bs8（batch 消融）、hybrid_gate_llm（门控+LLM 复核）、qwen25_coder_05b_shared、qwen3_06b_shared、qwen3_coder_small_shared、rules_baseline（规则下界），共 7 项
- **灰区配置**：三桶门控并列记录两套——**配置A [0.15, 0.85)**（hybrid LLM 复核实际执行口径）与 **配置B [0.20, 0.80)**（标定口径），详见 §1.3 与附录 B

---

## 0. 摘要（TL;DR）

1. **CodeBERT（bs16，部署版）为综合最优底座**：校准后 F1 0.8599、AUC 0.9545；推理吞吐 ~22.4 条/s，是 Qwen 系（5.15–7.25 条/s）的 **3–4.3 倍**；训练快 2.3–3.2×、权重体量小 4.6×（0.5GB vs 2.3–2.4GB）。
2. **hybrid（CodeBERT 三桶门控 + LLM 灰区复核）查准最优**：Precision 0.8739 → **0.9017（配置A）/ 0.8902（配置B）**（均为全场最高），误报 FP 1,538 → **1,151（−25.2%）/ 1,314（−14.6%）**，F1 0.8599 → **0.8689 / 0.8674**；LLM 负载仅 **29.4%（7,353 条，配置A，实测）** / **26.3%（6,595 条，配置B，折算）**。⚠️ **LLM 复核分支存在 12,000 字符截断上限，灰区样本恶意线索若在截断区之外 LLM 不可见，故该组性能为参考值**；后续在 GUI 壳中随用户配置调整（LLM 接入/参数/门控阈值）后应以实测为准。
3. **batch 对齐消融揭示方法学陷阱**：裸测 F1 上 CodeBERT 对 Qwen2.5-Coder-0.5B 的"领先"在 batch 对齐后从 +0.49pt 缩水到 **+0.06pt（实质打平）**——底座差距大部分来自优化轨迹；但 AUC（操作点无关）CodeBERT 仍稳定领先 ~1.4pt，且校准后口径与效率优势不变。
4. **两域口径下，prompt 域是全体模型的失分主战场**：语料**只有两个域**——code（n=11,022）与 prompt（n=14,027）；评估器明细里那个占 80.8% 的 `other` 桶只是**前缀注册表未登记时的兜底归集**，其样本逐条归属这两域之一。校准后 **code 域召回 98.5%–99.2%**（近乎饱和），**prompt 域召回 63.1%–86.1%**——prompt 域才是差距所在，batch 对齐版 bs8 以 86.1% 显著领先其余方案（72.4% / 71.5% / 68.1% / 66.8% / 63.1%）。rules 基线在 prompt 域召回仅 **7.03%**（code 域尚有 75.05%），说明扩容数据确实拉出了模型间差距。
5. **rules_baseline 下界成立**：F1 0.5025，仅作无 GPU 兜底与对照锚点；其余场景不推荐。

## 1. 评测设置

### 1.1 数据与划分（v2.5）

| 项 | 值 |
|---|---|
| 原始语料 | 254,789 文件 / 26.10GB（恶意 129,415 / 良性 125,374） |
| 去重后入模 | 250,490（归一化层剔除 4,275：格式重复 3,440 + 跨标签矛盾 835） |
| 四段划分 | train 175,343 / val 25,049 / calib 25,049 / **test 25,049** |
| test 构成 | 恶意 12,596（50.29%）/ 良性 12,453（49.71%） |
| 泄露自检 | 18 项交叉校验全零（raw-sha / 归一化 sha / 家族，六对分段全 PASS） |
| 类别失衡 | 划分层恶意 125,911 vs 良性 124,579（差 0.5%，已确认接受不采样） |

> 说明：codebert_ft 评测产物中 `family_overlap_with_train=414` 已确证为评估器家族键口径缺陷导致的**假阳性**；按 train.py 权威家族键口径，test↔train = 0。划分与指标均不受影响。

### 1.2 域口径

语料**只分两个域**：`code`（代码 / 包类）与 `prompt`（提示词 / Skill / MCP 类）。归属按 `train.py` 的权威前缀映射 `_DOMAIN_BY_PREFIX` 判定（test 内）：

| 域 | n | 恶意 / 良性 | 覆盖来源 |
|---|---|---|---|
| code | 11,022 | 5,755 / 5,267 | py / npm / ide / twin / rb / go / jv 等代码包，以及扩容新增的 ps（PowerShell）、ws（Webshell） |
| prompt | 14,027 | 6,841 / 7,186 | ms / sb / atr / ch / sk / mcs 等提示词类，以及扩容新增的 pi（恶意 prompt）、skb（MaliciousSkillBench） |
| **合计** | **25,049** | 12,596 / 12,453 | **无第三域**；未映射前缀 = 0 |

> ⚠️ **关于"other 域"**：`evaluate.py` 的分域明细里会出现一个 `other` 桶（占 test **80.8%**，20,242 条），那是**评估器前缀注册表未登记时的兜底归集**，并非真实存在的第三个域——其中每一条按文件名前缀都属于 code 或 prompt 之一（v2.5 扩容的 ps/ws → code，pi/skb → prompt）。**本报告的分域口径一律以 `train.py` 权威映射（两个域）为准**，§5 的分域表已据此重算；`evaluate.py` 的域注册表待同步（否则每轮评测都会产出一个失效的 other 桶）。

### 1.3 指标口径

- **裸测**：logit > 0 直接判定（rules 为伪概率 0.2+0.15×命中数 ≥0.5 判恶意）；
- **校准后**：Platt 缩放（25,049 条 calib 段拟合），p > 0.5 判恶意——**本报告主口径**（与部署一致）；
- **三桶门控**：p < allow 阈值 → allow（静默放行）；allow ≤ p < block → llm_review（灰区，需复核）；p ≥ block → block。本报告**并列记录两套阈值**：
  - **配置 A = [0.15, 0.85)**：hybrid 的 LLM 复核**实际执行**所用口径（调用量 7,353、耗时 5,814.5s 均为该配置下的实测）；
  - **配置 B = [0.20, 0.80)**：阈值**标定推荐**口径（指标由 A 批次逐样本 LLM 判定按新桶边界回放重算；temperature=0，判定确定，故回放忠实）。
- **silent_allow**：恶意样本落入 allow 桶被静默放行的条数（安全第一指标）；
- AUC / ECE（15 桶）/ Brier 全模型统一口径计算（由概率分布直接得出，**与灰区配置无关**）。
- **并列写法约定**：后文凡受灰区影响的取值，一律按 `配置A / 配置B` 并列（如 `126 / 161`）；两配置相同处只写一个值。

统一训练配置：lr=2e-5 / epochs=3 / seed=42（HPO 网格 6 组在 val 段选优，best val_f1 0.9075）；Platt 全部 A<0，单调方向一致，校准映射健康。

> **口径注（val_f1 0.9075 与 test F1 不可直接相减）**：0.9075 是 HPO 训练期 Trainer 在 **val 段**上的 **单窗口（512 token 截断）+ 裸测（logit>0）** F1，且 val 同时用于 6 组网格选参与 best-checkpoint（`metric_for_best_model=eval_loss`）选择，本身偏乐观（`hposearch.py` 明文声明 val 指标"禁止对外引用"）；而 test 各 F1 是 `evaluate.py` 的 **全文滑窗（512/stride256，取 max 聚合）+ Platt 校准**、且 test 从不参与任何选择。差距拆解：val 0.9075 → test 裸测 0.8734（−3.4pt，口径 + 选择偏差）→ test 校准后 0.8599（−1.35pt，操作点移动）。**差异来自口径与选择偏差，非数据分布**（group-aware 划分，18 项泄露校验全零，val/test 恶意占比 50.2% / 50.3%）。

### 3.3 排序解读

1. **裸测口径**：CodeBERT(bs16) 0.8734 > CodeBERT(bs8) 0.8691 > Qwen2.5-Coder 0.8685 > Qwen3-CoderSmall 0.8582 > Qwen3-0.6B 0.8572。前三名差距 <0.5pt——**在 batch 未对齐时读出的"底座差距"大部分是优化轨迹差异**（详见第 6 节消融）。
2. **校准后口径**（主口径）：hybrid 0.8689 / 0.8674（配置A / B）≈ bs8 0.8672 > codebert_ft 0.8599 > Qwen2.5-Coder 0.8396 > Qwen3-0.6B 0.8294 ≈ Qwen3-CoderSmall 0.8276。CodeBERT 校准后仅损失 0.2–1.4pt，Qwen 系校准后损失 2.8–3.1pt（操作点向低误报移动更多、召回让渡更大），故 CodeBERT 与 Qwen 的差距从裸测的 ~0.5pt 拉大到校准后的 **~2.0–4.1pt**。
3. **AUC（与操作点无关的判别力）**：CodeBERT 0.9545 / bs8 0.9526 稳定领先 Qwen 系（0.9390–0.9401）约 **1.3–1.5pt**——这才是底座判别力的真实差距。
4. **P/R 权衡形态**：bs8 与裸测各模型是"高召回低查准"型（R 92–96%、P 78–82%）；codebert_ft 校准后与 hybrid 是"均衡偏查准"型（P 87–90%）。**安全产品通常更缺查准**（误报直接消耗人工审计预算），hybrid 的 P 0.9017 / 0.8902（配置A / B）为全场最高（次高 codebert_ft 0.8739）。
5. **rules_baseline** F1 0.5025 介于微调模型与随机猜测之间，"下界参照"定位成立；其 AUC 0.6283 说明伪概率几乎没有排序能力，无法用于门控分流。

| 方案 | F1 裸测 → 校准后 | Δ | ECE 裸测 → 校准后 | 灰区(review) 裸测 → 校准后：配置A / 配置B |
|---|---|---|---|---|
| codebert_ft | 0.8734 → 0.8599 | −1.35pt | 0.066 → 0.052 | 7,832→7,353 / 6,978→6,595 |
| codebert_ft_bs8 | 0.8691 → 0.8672 | −0.19pt | 0.072 → 0.057 | 5,456→6,105 / 3,825→5,308 |
| qwen25_coder_05b | 0.8685 → 0.8396 | −2.89pt | 0.093 → 0.059 | 7,400→7,444 / 6,236→6,213 |
| qwen3_06b | 0.8572 → 0.8294 | −2.77pt | 0.095 → 0.060 | 5,806→8,288 / 4,059→6,795 |

- 校准统一把操作点拉向"高查准、低误报"，代价是召回让渡——对安全产品是正确方向（漏报进入 review 桶仍可被复核兜住，误报直接放行为 block 则消耗人工）；
- 校准后全部模型 ECE ≤ 0.062（裸测最高 0.095），概率可直接用于阈值分桶与置信度展示；
- qwen3_06b / qwen3_coder_small 校准后灰区桶（人工/LLM 复核工作量）膨胀至 8.3k / 8.3k（占 test 33.1% / 33.3%，配置A）、6.8k / 7.1k（27.1% / 28.2%，配置B），比 CodeBERT 的 7,353（29.4%）/ 6,595（26.3%）多 3–13%；qwen25 基本持平。

### 4.2 安全指标解读

- **静默放行（allow 桶恶意）**：codebert_ft 在两套配置下均最少——**126（1.52%，配置A）/ 161（1.85%，配置B）**；其后依次 qwen25（144 / 235）、qwen3_coder_small（157 / 275）、qwen3_06b（162 / 353），bs8 最多（**358 / 547**）——bs8 的高召回是把更多样本推向 block/review 换来的，但 allow 口子也松得多。**rules 因伪概率最小值 0.2 已高于两套配置的 allow 阈值（0.15 / 0.20），allow 桶恒空（公式固有性质）**，但这不代表安全：其漏报（7,796 条）几乎全部落在 review 桶内（该桶含 8,460 条恶意，配置A；8,084 条，配置B），复核压力是 codebert_ft（3,455 / 3,271 条）的 **2.5 倍**。
- **block 桶纯度**（拦截后需人工确认的比例）：codebert_ft 最高——95.7%（配置A）/ 94.0%（配置B），每 17–21 条拦截里 16–20 条真恶意；rules 仅 76.7% / 76.4%。
- **review 桶复核成本**：神经模型灰区 6.1k–8.3k 条/万（test 的 24–33%，配置A）、5.3k–7.1k（21.2–28.2%，配置B）。两套配置的取舍：配置A 灰区更大但把 LLM 价值最高的 [0.80,0.85) 留在复核内；配置B 复核量少 10.3%，代价是 block 口更硬、误拦上升。
- **校准的方向（易误读：须把"误拦"与"静默放行"分开陈述）**：Platt 把操作点移向高查准，p>0.5 处**误报 FP 大幅下降**（codebert_ft 2,690→1,538，−42.8%；Recall 0.9408→0.8464 为代价）；**但 allow 桶的静默放行同时变多，五个模型在两套配置下全部同向**（下表并列 A / B）：

| 模型 | FP（p>0.5）裸测→校准 | 静默放行：配置A（p<0.15）裸测→校准 | 静默放行：配置B（p<0.20）裸测→校准 |
|---|---|---|---|
| codebert_ft | 2,690 → 1,538（−42.8%） | 67 → 126（+88.1%） | 87 → 161（+85.1%） |
| codebert_ft_bs8 | 2,985 → 2,545（−14.7%） | 237 → 358（+51.1%） | 282 → 547（+94.0%） |
| qwen25_coder_05b | 3,164 → 1,681（−46.9%） | 46 → 144（+213.0%） | 78 → 235（+201.3%） |
| qwen3_06b | 3,269 → 1,902（−41.8%） | 116 → 162（+39.7%） | 172 → 353（+105.2%） |
| qwen3_coder_small | 3,163 → 1,606（−49.2%） | 118 → 157（+33.1%） | 151 → 275（+82.1%） |

  即**校准降低的是"误拦"，放松的是"静默放行"**——校准后的概率分布把更多边界样本压到阈值线以下（allow 桶总量 7,203→8,279（配置A）/ 7,714→8,707（配置B）），是可解释的权衡，但**静默放行是第一安全指标，不能表述为"收紧"**。该副作用由阈值兜底（配置B 的 allow 阈值 0.20 比 A 更紧，正是为此），而非依赖校准本身。

## 5. 分域与分来源表现

### 5.1 两域对比（校准后）

> 口径：按 `train.py` 权威前缀映射归入**两个真实域**（见 §1.2），评估器明细里的 `other` 桶已拆回 code / prompt。
> "静默放行"为**配置A（p<0.15）**口径下被直接放行的恶意条数；配置B（p<0.20）见各表括号。

**code 域**（n=11,022，恶 5,755 / 良 5,267）——微调模型近乎饱和，差异集中在良性误报：

| 方案 | 召回 | 静默放行 | 良性误报（率） |
|---|---|---|---|
| codebert_ft | 99.17% | 22 | 778（14.8%） |
| hybrid*（配置A / 配置B） | 98.45% / 98.75% | 22 / 25 | **320（6.1%）/ 460（8.7%）** |
| codebert_ft_bs8 | 99.08% | 41 | 878（16.7%） |
| qwen25_coder_05b | 98.58% | 48 | 982（18.6%） |
| qwen3_06b | 99.13% | 19 | 1,190（22.6%） |
| qwen3_coder_small | 99.15% | 23 | 1,113（21.1%） |
| rules_baseline | 75.05% | 0 | 1,260（23.9%） |

**prompt 域**（n=14,027，恶 6,841 / 良 7,186）——**主战场**：

| 方案 | 召回 | 静默放行 | 良性误报（率） |
|---|---|---|---|
| codebert_ft_bs8 | **86.07%** | 317 | 1,667（23.2%） |
| codebert_ft | 72.42% | 104 | 759（10.6%） |
| hybrid*（配置A / 配置B） | 71.54% / 72.66% | 104 / 136 | **831（11.6%）/ 854（11.9%）** |
| qwen25_coder_05b | 68.09% | 96 | 699（9.7%） |
| qwen3_06b | 66.77% | 143 | 709（9.9%） |
| qwen3_coder_small | 63.12% | 134 | 492（6.8%） |

> 域内 F1（校准后，配置A）——code 域：codebert_ft 0.9325 / bs8 0.9245 / qwen25 0.9143 / qwen3_coder_small 0.9076 / qwen3_06b 0.9020 / rules 0.7621；
> prompt 域：bs8 0.8180 / codebert_ft 0.7892 / qwen25 0.7637 / qwen3_06b 0.7539 / qwen3_coder_small 0.7412 / rules 0.1238。

### 5.2 解读

1. **code 域近乎饱和**：微调模型召回 98.5%–99.2%，差异只在良性误报。该域良性样本本来就"长得危险"（打包/混淆常见），误报率 14.8%–23.9% 偏高，是**误报治理**（而非召回）问题；hybrid 的 LLM 复核在该域把误报降 58.9%（配置A：778→320）/ 40.9%（配置B：778→460）。
2. **prompt 域才是差距所在**：bs8（86.1%）> codebert_ft（72.4%）> hybrid（71.5%）> qwen25（68.1%）> qwen3_06b（66.8%）> qwen3_coder_small（63.1%）≫ rules（7.0%）。该域以提示词 / Skill / MCP 类内容为主（扩容新增的 pi / skb 亦归此域），**模型间整体 F1 差距几乎全部来自这里**。注意 bs8 与 codebert_ft 在 prompt 域的召回差（+13.7pt）正是两者 P/R 形态差异的缩影：bs8 桶口更松（静默放行 317 vs 104），以安全余量换召回；部署取 codebert_ft（bs16）是更稳妥的选择。
3. **两域的相对难度已被 rules 暴露**：规则基线在 code 域召回 75.1%，而 prompt 域仅 **7.0%**——规则天然擅长"危险 API / 混淆编码"这类代码侧信号，对自然语言提示注入几乎无能，这是纯规则方案不可用的直接证据，也说明 prompt 域需要的是语义理解而非模式匹配。
4. **来源级误报热点**（校准后，节选，hybrid 按 配置A / 配置B）：ben_npm codebert_ft 157/174（90%）→ hybrid **122 / 140**（70.1% / 80.5%）；ben_py 144/225（64%）→ hybrid **39 / 70**（17.3% / 31.1%）；ben_atr 131/341（38%）→ hybrid **11 / 20**（3.2% / 5.9%）。**老牌精标良性集（npm/pypi 包）是误报重灾区**，LLM 复核对 ben_atr / ben_py 修复明显、对 ben_npm 收效有限；Qwen 系在 ben_atr 上误报控制最好（86–128 条）。

## 7. hybrid_gate_llm 专项分析

### 7.1 机制与收益

机制：codebert_ft（bs16）校准概率三桶分流（灰区可配：配置A [0.15,0.85) / 配置B [0.20,0.80)）；灰区（review 桶）交 DeepSeek（v_feature 模板，val 抽样挑模板胜出）复核，LLM 失败保守判恶意。allow/block 桶与 codebert_ft 完全一致。两套配置对比如下：

| 指标 | ft（纯门控） | +LLM：配置A [0.15,0.85) | +LLM：配置B [0.20,0.80) |
|---|---|---|---|
| F1 | 0.8599 | **0.8689（+0.90pt）** | 0.8674（+0.75pt） |
| Precision | 0.8739 | **0.9017（+2.78pt）** | 0.8902（+1.63pt） |
| Recall | 0.8464 | 0.8384（−0.80pt） | 0.8458（−0.06pt） |
| 误报 FP | 1,538 | **1,151（−387，−25.2%）** | 1,314（−224，−14.6%） |
| 漏报 FN | 1,935 | 2,036（+101） | 1,942（+7） |
| LLM 调用量 | — | 7,353（29.4%） | 6,595（26.3%） |

- **配置A 收益更大、代价更高**：灰区把 LLM 价值最高的 [0.80,0.85) 带纳入复核（该带 LLM 净收益 +80），故误报降幅 25.2% 明显优于配置B 的 14.6%；代价是 LLM 调用多 11.5%、且 [0.15,0.20) 低价值带白跑复核。配置B 复核更省，但 block 口更硬、误拦上升。
- **LLM 改动胜率均刚过半**：配置A 复核桶内 3,300 次改判中改对 1,793 / 改错 1,507（54.3%）；配置B 3,005 次改判中改对 1,611 / 改错 1,394（53.6%）。"改对"主要来自释放良性、"改错"为放走恶意，**在"误报成本 ≫ 漏报成本×复核兜底"的运营假设下两配置均为正收益**。
- 复核批次异常率：api_error 0 / parse_error 0。

### 7.2 ⚠️ 截断上限注记（性能为参考值）

- **门控主干（CodeBERT 滑窗 max_length 512 / stride 256）对全文滑窗，无截断**；allow/block 桶结论不受影响。
- **LLM 复核分支输入仅取清洗文本前 12,000 字符**（适配层常量 `TEXT_MAX_CHARS=12000`）。灰区源文件 >12KB 的占比：配置A **668/7,353（9.1%）**、配置B **500/6,595（7.6%）**（清洗后实际截断率低于此值）——**恶意线索若位于 12k 之后，LLM 不可见，判定可能失真**（如长包尾部的 postinstall 持久化逻辑）。
- 因此 **7.1 节全部数字为参考值**，且属于特定配置（DeepSeek v_feature 模板、12k 截断、两套门控阈值）下的结果；逐样本 LLM 判定取自已执行的复核批次（temperature=0，判定确定），配置B 的桶归属与调用量按 [0.20, 0.80) 回放重算。
- **后续方向**：在 GUI 壳中该方案为配置驱动，用户可随需调整——门控阈值（config.yaml 的 allow/block）、LLM 接入与参数（gui-settings.json / 引擎 config：api_key、base_url、model、temperature、max_tokens、timeout、evidence_max_chars）、截断上限等；调整后的实际表现应以用户配置下的重测为准。

## 8. batch 对齐消融（方法学）

| 口径 | codebert_ft（bs16） | codebert_ft_bs8 | 差距 |
|---|---|---|---|
| 裸测 F1 | 0.8734 | 0.8691 | −0.43pt |
| 裸测 F1 vs Qwen2.5-Coder（0.8685） | +0.49pt | +0.06pt | **对齐后实质打平** |
| 校准后 F1 | 0.8599 | 0.8672 | bs8 反超 +0.73pt |
| 裸测 P / R | 0.8150 / 0.9408 | 0.8005 / 0.9507 | bs8 更偏召回 |
| 校准后 P / R | 0.8739 / 0.8464 | 0.8200 / 0.9201 | 形态分化 |
| 静默放行（配置A / 配置B） | 126 / 161 | 358 / 547 | bs8 口子更松 |
| 训练耗时 | 2.43h | 2.54h（步数×2、单步减半，净慢 4%） | — |

- **结论一**：未对齐 batch 时，"底座优势"混入了优化轨迹差异（有效 batch/总步数/warmup/LR 衰减曲线均不同）；对齐后裸测层面 CodeBERT 与最强 Qwen 打平。
- **结论二**：底座选择的真实依据是——AUC 稳定领先 1.3–1.5pt、推理吞吐 3–4.3×、体量与训练成本优势（第 6 节），而非裸测 F1 的表面差距。
- **决策（已定）**：部署版 = bs16（与机房 v0.2.2 训练口径一致）；bs8 版仅作消融对照存档，不替换。

## 9. 结论与部署建议

| 场景 | 推荐 | 依据 |
|---|---|---|
| **默认部署（GUI 壳内置）** | **codebert_ft（bs16）** | 校准后 F1 0.8599 / AUC 0.9545 / ECE 0.052；block 纯度 95.7%（A）/ 94.0%（B）、allow 危险率 1.52%（A）/ 1.85%（B）；吞吐 ~22 条/s、权重 0.5GB，单卡/低配可跑 |
| 追求查准、可接受 API 依赖与复核延迟 | **hybrid_gate_llm** | P 0.9017（配置A）/ 0.8902（配置B）均全场最高；误报 −25.2%（A）/ −14.6%（B）；LLM 负载 29.4%（A）/ 26.3%（B）。⚠️ 受 12k 截断上限影响为参考值，GUI 壳配置调整后以实测为准 |
| 无 GPU / 断网兜底 | rules_baseline | F1 0.5025 但零依赖、292 条/s；仅作下界与降级路径，非运营方案 |
| 不推荐 | Qwen 系底座 | 判别力（AUC）落后 1.3–1.5pt，吞吐慢 3–4.3×、体量大 4.6×；保留为多底座消融结论存档 |

**后续迭代方向**（按投入产出排序）：

1. **prompt 域召回**是全体模型的最大失分区（63.1%–86.1%；code 域已达 98.5%+），优先做该域的难例分析（提示注入变体、Skill / MCP 类载体）与针对性增强；
2. **良性误报治理**：code 域老牌精标良性集（ben_npm 90%、ben_py 64% 误报）值得扩充良性语料或引入"已知良性白名单"机制；
3. hybrid 截断上限放开（分段滑窗送 LLM 或提高上限）后重测，验证 0.8689 / 0.8674（配置A / B）的参考值是否还可上探；
4. 若需精细延迟数据，补跑云端 `speed --all` 产 speed_gpu.json（分档 short/medium/long 时延）。

| [0.70, 0.80) | 459 | 39–42% | 高侧模糊带，LLM 净收益 +121 → 两配置均保留在灰区内 |
| [0.80, 0.85) | 330 | 45.2% | **两配置的分界带**：LLM 净收益 +80（有真实价值，配置A 保留），但该带良性 181 条占 55%，归 block 后误拦上升（配置B 切掉） |

两侧拐点定义：**低侧 = 恶意率断崖起点**（0.15 保低险率 / 0.20 收紧 allow）；**高侧 = block 纯度约束**（0.85 保 95.7% 纯度 / 0.80 收缩至 94.0%）。

**先验稳健性（仅配置B满足，容量规划可用）**：配置B 的 `P(送LLM｜恶意)=25.97%`、`P(送LLM｜良性)=26.69%`，仅差 0.7pt——LLM 负载**几乎与真实上传的恶意先验无关**（纯良性流量 26.7%、恶意占比 70% 时 26.2%）。配置A 则相反（`P(送LLM｜恶意)=27.4%` vs `P(送LLM｜良性)=31.3%`，倒挂 3.9pt）：**纯良性流量下反而更烧 LLM 额度**。故若按容量系数规划，用配置B 的 26% 更稳。

### B.4 生效条件与遗留

1. 两套标定均基于 **v2.5 bs16 模型 + 其 Platt 校准参数**（A=−1.0332 / B=0.7344）的概率分布，须成对部署；**GUI 壳若内置旧版模型，其概率分布不同，须重新标定**（配置点即 `allow_threshold` / `block_threshold`，GUI 后续暴露为用户可调项）。
2. 落地动作：按选定配置改引擎 `config.yaml` 的 `allow_threshold` / `block_threshold`（配置A 为 0.15/0.85，即引擎当前默认；配置B 为 0.20/0.80）。
3. 遗留观察：两配置的 block 侧均无条件拦截高概率带，而 [0.80, 0.90) 局部良性占 39.9%（Platt 中段拉伸所致）。若运营中误拦申诉集中，可将 block_threshold 提至 0.90（灰区 +404）换回约 161 条良性误拦，按实际申诉数据决定。
